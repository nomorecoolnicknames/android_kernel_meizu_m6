# M6 hwcomposer lane — 2026-08-03

Lane: `hwc-lane`. Task: port the m681 hwcomposer fixes to the M6 (meizu_m6,
MT6750, kernel 3.18.140, LOS 16.0) and bring composition to a working state.

## Verdict up front

**Composition on the M6 is ALREADY WORKING through the real MTK HWC blob**, and
the m681 hwcomposer fix cascade does **not** transfer — it was almost entirely a
4.4-kernel-vs-Nougat-blob ABI problem that the M6, running its native 3.18
blob-era kernel, does not have. What this lane found instead is that the M6's
composition works **by accident in three separate places**, each one refactor
away from breaking. The delivered changes make those accidents explicit and
deliberate. Zero behaviour change expected on the current boot; the payload is
correctness of *future* builds.

## 1. What m681 actually fixed in hwcomposer (from the m681 docs)

Source: `/srv/forge/android/m681/docs/M681_HANDOFF_TO_LOS16.md:180-235` ("The
five roots"), `:2469-2560` (HWC2On1Adapter investigation), `:2647-2700`
(baseline triage).

| m681 fix | Nature | Applies to M6? |
|---|---|---|
| 1. `graphics.composer` HAL never declared in vendor manifest → SF aborted (`failed to get hwcomposer service`) | userspace manifest | **Partially** — M6 manifest also lacks the entry, but M6's SF demonstrably survives via the libhidl legacy fallback (see §3). Entry added for parity/hardening. |
| 2. `disp_session_info` ABI drift (`maxLayerNum` read from wrong offset) | kernel 4.4 shim | **NO** — M6 kernel 3.18.140 is the blob-era kernel; the disp UAPI is the one the blob was compiled against. |
| 3. `FRAME_CONFIG` (ioctl 220) struct drift, 144 vs 160 B layer stride | kernel 4.4 shim | **NO** — same reason. |
| 4. shim helpers passed kernel pointers to `copy_from_user` | bug in m681's own shims | **NO** — M6 has no such shims. |
| 5. light HAL phantom (blocked boot, not hwc proper) | build system | Already handled on M6 (other lane; `init.svc.vibrator/light` alive, boot completes). |
| `HWC2On1Adapter.cpp` reorder/dlopen/retry hack (`debc8ae`) | userspace | **NO — and must not be ported.** m681 proved it was never compiled, never load-bearing, and reverted it (`624e6af`). The tree both devices share already carries the revert. |
| `liblog __xlog_buf_printf` / `libcutils android_atomic_*` / `IInterface::asBinder` 64-bit ABI | userspace, shared tree | Already present — same ROM tree (`/home/gun/m6rom16/rom`), and the M6 blob loads/runs (§2), which is the live proof the symbols resolve. |

**Conclusion (INFERENCE from the table):** there is no m681 hwcomposer patch
left to port. The m681 display root causes lived in the kernel↔blob ABI gap
that the M6 does not have.

## 3. The three accidents found (why it works, and why that was fragile)

### 3a. The HWC module is found through LK's cmdline, not through the device tree

- **FACT**: the only HWC module on the image is
  `/system/vendor/lib{,64}/hw/hwcomposer.mt6755.so` (`find /system /vendor
  -name "hwcomposer*"` returns exactly those two). There is **no**
  `hwcomposer.mt6750.so` and no `hwcomposer.default.so`.
- **FACT**: the device tree pointed the loader at the nonexistent name:
  `device_meizu_m6.mk:71` and `system.prop:144` set
  `ro.hardware.hwcomposer=mt6750`.
- **FACT**: `hw_get_module` (stock `hardware/libhardware/hardware.c`, verified
  stock by strings + md5 both on device and in out) falls back through
  `ro.hardware` — and live `getprop ro.hardware` = **mt6755**, because LK's
  baked cmdline provides `androidboot.hardware=mt6755` (`ro.boot.hardware` =
  mt6755) and init sets `ro.hardware` from it before any prop file loads;
  `ro.*` is first-wins, so the mk's `ro.hardware=mt6750` override never lands.
  (Same LK behaviour as documented for m681 in
  `M681_HANDOFF_TO_LOS16.md:2600-2640`.)
- **INFERENCE**: composition therefore only worked because the bootloader's
  cmdline shadowed a wrong device-tree value. Any change to LK, cmdline
  handling, or a future `ro.hardware` override in `default.prop` (which CAN
  win, being loaded first) would have silently killed HWC.
- **Fixed**: `ro.hardware.hwcomposer=mt6755` in both places.

### 3b. The blob was filtered out of PRODUCT_COPY_FILES — and shipped anyway

- **FACT**: `device_meizu_m6.mk:547-548` and `lineage.mk:150-151` (the
  authoritative product per `AndroidProducts.mk` name:path mapping) both
  filtered `%:system/vendor/lib{,64}/hw/hwcomposer.mt6755.so` out of
  `PRODUCT_COPY_FILES`, while the current vendor mk
  (`vendor/meizu/meizu_m6/meizu_m6-vendor-blobs.mk:236,260`) installs the blob
  ONLY under that dest.
- **FACT**: the Jul 25 image nonetheless contains the blob (out tree +
  device, md5 match) — the filters did not bite.
- **INFERENCE (mechanism)**: `inherit-product` merges inherited
  `PRODUCT_COPY_FILES` after the inheriting makefile is parsed, so a
  `filter-out` in `device_meizu_m6.mk` / `lineage.mk` cannot see entries
  contributed by `vendor/meizu/meizu_m6/meizu_m6-vendor.mk`
  (`lineage.mk:378`). The filters are inert.
  **Verified post-edit** via `get_build_var PRODUCT_COPY_FILES` (see §5).
- **History (INFERENCE)**: the filters date from the original cm-14.1-era tree
  whose `proprietary-files.txt:249,273` RENAMED the blob to
  `hwcomposer.mt6750.so` on extraction and filtered the mt6755-named
  duplicates. The rename scheme is gone; the filters stayed.
- **Fixed**: both hwcomposer filter lines removed (gralloc/keystore filters
  left untouched — `gralloc.mt6750.so` is the name both the prop and the image
  agree on, and it ships).

### 3c. The composer HAL is undeclared and loads through the legacy fallback

- **FACT**: `/vendor/manifest.xml` on the device (and its source
  `device/meizu/meizu_m6/manifest.xml`) has **no**
  `android.hardware.graphics.composer` entry; `ps` shows no composer service
  process; the impl loads into SF regardless (pid evidence above).
- On m681 the identical omission was fatal (`M681_HANDOFF_TO_LOS16.md:188-190`)
  and the fix was the manifest entry, live-verified 2026-07-27 and landed in
  `device/meizu/m681/sepolicy/manifest.xml` with a detailed comment.
  Why the M6 survives where m681 died is **not resolved** (HYPOTHESIS: some
  enforcement-relevant difference — m681's manifest/first-api-level/treble
  configuration at the time; not worth chasing while both configurations now
  declare the entry).
- **Fixed**: composer 2.1 passthrough `arch="32+64"` entry added to
  `device/meizu/meizu_m6/manifest.xml`, copied from the m681-proven block.

### 3d. (prop hygiene) Two dead "HWC off" switches contradicted a documented fix

- **FACT**: `device_meizu_m6.mk:78-79` set `debug.sf.disable_hwc=1` and
  `debug.composition.type=gpu`, and won the build.prop dedupe over
  `system.prop:172`'s `debug.sf.disable_hwc=0` (live getprop showed `1`/`gpu`),
  directly contradicting system.prop's 2026-06-21 comment that names
  `disable_hwc=1 + composition.type=gpu` as the historical UI-lag cause.
- **FACT**: on THIS stack both props are read by nobody — `grep -rn disable_hwc
  frameworks/native/services/surfaceflinger/` = 0 hits (Pie SF has no such
  prop), and `strings` of `hwcomposer.mt6755.so` shows the blob reads only the
  `debug.hwc.*` family (`compose_level`, `bq_count`, …), `debug.sf.sw_vsync_fps`
  and `ro.sf.*`. That is why HWC ran fine despite `disable_hwc=1` — the switch
  is connected to nothing.
- **Fixed**: both lines removed from `device_meizu_m6.mk`; `system.prop`'s
  documented `debug.sf.disable_hwc=0` now stands unopposed (itself inert on
  Pie, kept as documentation). `debug.hwc.compose_level=0` (full HWC
  composition) and `debug.hwc.bq_count=4` are live and already at the good
  values — untouched.
